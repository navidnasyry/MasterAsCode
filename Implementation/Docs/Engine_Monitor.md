# عامل پایش بی‌درنگ موتورها (Engine Monitor)

**مسیر کد:** `Implementation/engine-monitor/`  
**پورت UI:** `3001` → nginx:80 داخل کانتینر  
**منبع داده:** LSTM RUL API (`:8000`)

---

## ۱. روش‌شناسی (Methodology)

### ۱.۱ هدف

عامل پایش، وضعیت سلامت ناوگان را بر اساس پیش‌بینی RUL به‌صورت شبه‌بی‌درنگ نمایش می‌دهد. زمان شبیه‌سازی‌شده (\(t_{\mathrm{clock}}\)) با گام ثابت جلو می‌رود و در هر تیک، موتورهایی که \(\hat{y}_k < \theta\) هستند از API پیش‌بینی دریافت و روی کارت‌ها نمایش داده می‌شوند.

### ۱.۲ منطق طبقه‌بندی وضعیت

با آستانهٔ پیکربندی‌شده \(\theta\) (پیش‌فرض UI: ۵۰ چرخه):

| شرط | برچسب UI |
|-----|----------|
| \(\hat{y} < \theta/2\) | Critical |
| \(\theta/2 \le \hat{y} < \theta\) | Warning |
| در غیر این صورت | در فهرست low-RUL نمی‌آید |

این منطق با آستانهٔ بحرانی عامل زبانی در Dify (\(\theta=30\)) می‌تواند متفاوت باشد؛ هر دو قابل پیکربندی‌اند و در ارزیابی باید صریح گزارش شوند.

### ۱.۳ شبیه‌سازی جریان زمان

\[
t \leftarrow 0,\qquad
t \leftarrow t + \Delta t \quad \text{هر } T_{\mathrm{interval}}\ \mathrm{ms}
\]

در هر گام، درخواست زیر صادر می‌شود:

`GET /api/predict/engines_with_low_rul/?threshold=θ&until_clock=t`

پارامتر `until_clock` تضمین می‌کند که پیش‌بینی فقط با داده تا افق زمانی جاری انجام شود؛ این همان قرارداد لایهٔ جمع‌آوری دادهٔ شبیه‌سازی‌شده است.

### ۱.۴ پارامترهای پیش‌فرض (`constants.js`)

| پارامتر | مقدار پیش‌فرض |
|---------|----------------|
| threshold | ۵۰ |
| step (Δt) | ۳۰ چرخه |
| interval | ۵۰۰۰ ms |

## ۲. پیاده‌سازی (Implementation)

### ۲.۱ پشته فناوری

| جزء | فناوری |
|-----|--------|
| UI | React 18 + Create React App |
| HTTP | axios ^1.6 |
| سرو | nginx در ایمیج production |
| Runtime config | `docker-entrypoint.sh` → `runtime-config.js` |

### ۲.۲ ساختار کلیدی

```
engine-monitor/
├── src/
│   ├── App.js                 # حلقهٔ Start/Stop و clock
│   ├── services/api.js        # fetchEngineData، health، demo fallback
│   ├── utils/constants.js
│   └── components/
│       ├── Dashboard/         # Dashboard, EngineCard, StatsPanel
│       ├── Config/ConfigModal.js
│       └── Layout/Header.js   # health هر ۳۰s
├── nginx.conf(.template)
└── docker-compose.yaml        # 3001:80
```

### ۲.۳ قرارداد کلاینت-API

| فراخوانی | مقصد |
|----------|------|
| `GET {API_BASE}/predict/engines_with_low_rul/?threshold=&until_clock=` | lstm-rul-api |
| `GET {API_BASE}/health` | lstm-rul-api |

`API_BASE` از `window.RUNTIME_CONFIG.REACT_APP_API_BASE_URL` خوانده می‌شود؛ در Compose برابر `http://${HOST_IP}:8000/api` است.

### ۲.۴ مدیریت خطا

- Interceptorهای axios خطا را لاگ می‌کنند.
- در خطای شبکه، دادهٔ demo تولید می‌شود تا UI خالی نماند (مناسب دمو؛ باید در متن پایان‌نامه به‌عنوان حالت fallback ذکر شود).
- Header وضعیت healthy/unhealthy را نشان می‌دهد.

## ۳. ارزیابی و نتایج (Results)

### ۳.۱ شواهد بصری

| وضعیت سامانه | فایل تصویر |
|--------------|------------|
| همه موتورها خاموش / بدون موتور بحرانی فعال | `Images/عامل پایش برخط موتور‌ها - در حالت خاموش بودن همه موتور‌ها.png` |
| پس از روشن کردن همه موتورها | `Images/عامل پایش برخط موتور‌ها - پس از فرمان روشن کردن همه موتور‌ها.png` |
| پس از خاموش کردن موتورهای در خطر | `Images/عامل پایش برخط موتور‌ها- پس از فرمان خاموش کردن موتور‌های در خطر خرابی.png` |
| نسخهٔ دوم همان سناریو | `Images/عامل پایش برخط موتور‌ها - پس از فرمان خاموش کردن موتور‌های در خطر خرابی - نسخه ۲.png` |

**تحلیل فنی:** تصاویر نشان می‌دهند که UI پایش به تغییرات ناوگان واکنش می‌دهد و پس از فرمان‌های عامل زبانی، مجموعهٔ موتورهای نمایش‌داده‌شده (یا وضعیت عملیاتی مرتبط) تغییر می‌کند. این هم‌ترازی، یکپارچگی حلقهٔ «پیش‌بینی → تصمیم زبانی → کنترل دوقلو → بازخورد بصری» را تأیید می‌کند.

### ۳.۲ دموی ویدیویی

- `Demos/دموی عامل زبان طبیعی به همراه عامل پایش بی درنگ دوقلوهای دیجیتال.webm`

### ۳.۳ نکات ارزیابی کیفی

- تأخیر ادراک‌شده در UI عمدتاً مجموع `interval` پایش + Latency API LSTM است؛ نه Latency عامل زبانی.
- آستانهٔ ۵۰ در UI در برابر ۳۰ در Dify می‌تواند فهرست متفاوتی از «در خطر» تولید کند؛ برای آزمایش‌های قابل‌تکرار باید هر دو یکسان‌سازی شوند یا صریحاً گزارش شوند.
