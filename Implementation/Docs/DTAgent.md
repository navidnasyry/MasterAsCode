# سرویس دوقلوی دیجیتال موتورها (DTAgent)

**مسیر کد:** `Implementation/DTAgent/`  
**نام کانتینر:** `dt-engine-api`  
**پورت:** `8001`

---

## ۱. روش‌شناسی (Methodology)

### ۱.۱ نقش در معماری پنج‌لایه

DTAgent تحقق عملی دو لایه از معماری پیشنهادی است:

| لایه مفهومی | تحقق در DTAgent |
|-------------|-----------------|
| لایه موجودیت / جمع‌آوری داده | ارائه سری زمانی حسگرهای CMAPSS-FD001 به‌ازای هر موتور |
| لایه عامل‌های دوقلوی دیجیتال (وضعیت زنده) | نگه‌داری وضعیت کنترلی ON/OFF در حافظهٔ فرآیند |

جریان داده حسگری یک‌طرفه (از فایل شبیه‌ساز به مصرف‌کنندگان) است؛ جریان فرمان (روشن/خاموش) دوطرفه و از طریق API کنترل اعمال می‌شود. این ساختار امکان نمایش اثر تصمیم‌های عامل زبانی روی داشبورد وضعیت را فراهم می‌کند.

### ۱.۲ مدل وضعیت موتور

هر موتور با شناسهٔ صحیح \(k\in\{1,\ldots,N\}\) دارای حالت گسسته است:

\[
s_k \in \{\mathrm{ON},\,\mathrm{OFF}\}
\]

در راه‌اندازی، همهٔ موتورهای موجود در `test_FD001.txt` به \(\mathrm{ON}\) مقداردهی می‌شوند. تغییر حالت می‌تواند:
- انتخابی باشد: مجموعهٔ \(\mathcal{K}\) از شناسه‌ها؛
- سراسری باشد: همهٔ شناسه‌ها هم‌زمان.

### ۱.۳ دادهٔ حسگری

داده‌های خام از فایل آزمون CMAPSS خوانده می‌شوند. هر رکورد شامل شناسه، چرخه، سه تنظیم عملیاتی و ۲۱ حسگر است. پارامتر اختیاری `until_clock` امکان برش زمانی سری را برای سناریوهای شبیه‌سازی جریان داده فراهم می‌کند.

### ۱.۴ تمایز با Eclipse Ditto

اسکریپت `Implementation/init-dt/` مسیر قدیمی‌تر/جایگزین ایجاد Thing در Eclipse Ditto (`localhost:8080`) را نشان می‌دهد. پشتهٔ فعلی `docker-up.sh` از Ditto استفاده نمی‌کند؛ دوقلوی عملیاتی همان DTAgent است. در نگارش پایان‌نامه باید این تمایز صریح باشد.

## ۲. پیاده‌سازی (Implementation)

### ۲.۱ پشته فناوری

| جزء | فناوری |
|-----|--------|
| Framework | FastAPI + Uvicorn |
| زبان | Python 3.10 (ایمیج `python:3.10-slim`) |
| داده | pandas، numpy |
| ذخیره‌سازی وضعیت | دیکشنری در حافظهٔ فرآیند (بدون Redis/DB) |

### ۲.۲ ساختار ماژول‌ها

```
DTAgent/
├── app/
│   ├── main.py                 # CORS، startup، root
│   ├── api/routes_engine.py    # تمام endpointهای /engines
│   ├── services/engine_service.py
│   ├── models/engine_state.py  # engine_states: Dict[int,str]
│   └── core/config.py          # TEST_DATA_PATH
├── Dockerfile                  # EXPOSE 8001
└── docker-compose.yaml
```

### ۲.۳ APIها

**پایه:** `http://<host>:8001`

| Method | Path | ورودی | خروجی |
|--------|------|--------|--------|
| GET | `/` | — | پیام سلامت |
| GET | `/engines/{engine_number}` | `until_clock?: int` | `{"engine_number", "records":[...]}` |
| GET | `/engines/states/all` | — | فهرست `{engine_number, state}` |
| POST | `/engines/states/set?state=ON\|OFF` | Body: `[1,3,5]` | `updated_states` |
| POST | `/engines/states/set_all?state=ON\|OFF` | Query | همهٔ وضعیت‌ها |

### ۲.۴ رفتار کلیدی

- **Startup:** `initialize_engine_states()` شناسه‌های یکتا را از فایل می‌خواند و همه را ON می‌کند.
- **Cache:** دیتافریم حسگری در `_df_cache` نگه داشته می‌شود.
- **پایداری:** وضعیت ON/OFF با restart کانتینر از بین می‌رود و دوباره به ON بازمی‌گردد.

### ۲.۵ مدیریت خطا

| حالت | رفتار فعلی |
|------|------------|
| `state` نامعتبر در `set` | JSON `{"error":...}` با HTTP 200 |
| `state` نامعتبر در `set_all` | مسیر `HTTPException(400)` — نیاز به import صحیح `HTTPException` |
| موتور بدون داده | `records` خالی (بدون 404 صریح) |

### ۲.۶ یکپارچه‌سازی

| مصرف‌کننده | پیکربندی |
|------------|----------|
| motor-dashboard | `VITE_API_URL=http://HOST:8001/engines` → `GET /states/all` |
| Dify | `env.dt_host_addr` → POSTهای `set` / `set_all` |
| Volume داده | `./app/data` → `/app/app/data` |

## ۳. ارزیابی و نتایج (Results)

### ۳.۱ سناریوهای عملیاتی مشاهده‌شده

اثر فرمان‌های عامل زبانی روی وضعیت ناوگان در تصاویر زیر ثبت شده است:

| سناریو | تصویر |
|--------|--------|
| همه موتورها خاموش | `Images/عامل پایش برخط موتور‌ها - در حالت خاموش بودن همه موتور‌ها.png` (و داشبورد وضعیت مرتبط) |
| همه موتورها روشن | `Images/عامل پایش برخط موتور‌ها - پس از فرمان روشن کردن همه موتور‌ها.png` |
| خاموش‌سازی موتورهای در خطر | `Images/عامل پایش برخط موتور‌ها- پس از فرمان خاموش کردن موتور‌های در خطر خرابی.png` و نسخهٔ ۲ |

> توضیح: تصاویر پایش عمدتاً UI مربوط به `engine-monitor` را نشان می‌دهند؛ اثر کنترلی فرمان‌ها روی وضعیت ON/OFF در `motor-dashboard` و پاسخ‌های کوتاه عامل زبانی («عملیات با موفقیت انجام شد») تأیید می‌شود. تصاویر فرمان در `Images/تصویر مربوط به فرمان همه موتور‌ها را خاموش کن.png` و مشابه آن‌ها مربوط به عامل زبان طبیعی است.

### ۳.۲ محدودیت‌های مشاهده‌شده

- وضعیت در حافظه است؛ برای استقرار صنعتی به persistence نیاز است.
- مقیاس فعلی ۱۰۰ موتور FD001 است؛ الگوی API برای تعمیم به چند FD مناسب است ولی داده فقط FD001 بارگذاری شده.
- خطای نرم (HTTP 200 + error body) در برخی مسیرها ردیابی شکست را برای کلاینت‌های ساده دشوار می‌کند.

### ۳.۳ سخت‌افزار و اجرا

سرویس سبک است (بدون TensorFlow). در پشتهٔ Docker روی میزبان با `HOST_IP` شبکهٔ محلی اجرا می‌شود و برای پاسخ‌گویی به مرورگر و Dify باید از IP قابل‌دسترس کلاینت‌ها استفاده کند (نه فقط `localhost` داخل کانتینر).
